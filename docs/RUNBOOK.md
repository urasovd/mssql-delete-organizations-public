# Runbook: оставить в копии 1С выбранные организации

Конвейер для копии 1С на MS SQL. В базе остаются выбранные организации (одна или
несколько), а всё, что им не нужно, удаляется: документы, другие организации и,
по профилю, НСИ. Проверен на БИТ и ЗУП 3 — см. [разбор прогонов](CASE-STUDY.md).

Все скрипты без `-Apply` (или без своего токена) только читают базу. Работать
только с копией.

## Идея

1. **Каталог ссылок** строится заново из схемы хранения на каждом прогоне
   (`40`, SQLCLR-разбор `Config`/`Params`).
2. **KEEP** — то, что нужно сохраняемым организациям: объекты с их
   организацией, регистраторы их движений, предопределённые элементы, корни
   из политики и всё, на что они ссылаются (замыкание, `41`).
3. **DELETE** — дополнение: документы, другие организации, объекты только
   чужих организаций и объекты профиля вне KEEP; каскадом — объекты вне KEEP,
   у которых шапка ссылается на удаляемое.
4. **Граница** — ссылки остающихся строк на удаляемое. Каждый случай решается
   правилом в `policies/boundary-rules.csv` или останавливает прогон.

Что решено про объекты — [`policies/`](../policies/README.md). Что относится к
конкретной базе и выделению — [`configurations/`](../configurations/README.md).

## Быстрый путь

```powershell
$s = 'configurations\zup\example.settings.json'
.\scripts\Invoke-Extraction.ps1 -Settings $s -Stage Prepare                    # список организаций
.\scripts\Invoke-Extraction.ps1 -Settings $s -Stage Prepare -ConfirmationToken MARK-OTHER-ORGANIZATIONS
.\scripts\Invoke-Extraction.ps1 -Settings $s -Stage DryRun                     # 40 → 41 → 42 → 11, без изменений
.\scripts\Invoke-Extraction.ps1 -Settings $s -Stage Apply -ConfirmationToken DELETE-ALL-MARKED
.\scripts\Invoke-Extraction.ps1 -Settings $s -Stage Verify                     # 40 + 41 на результате, сверка 45
```

| Стадия | Что делает | Должно быть |
|---|---|---|
| `Prepare` | показывает организации; с токеном помечает на удаление все, кроме сохраняемых | все сохраняемые найдены |
| `DryRun` | каталог, KEEP/DELETE, план правил, холостое удаление; пишет `run.json` с хэшами | `coverage_gate=PASS`, `gate=PASS`, граница `PASS_SIMULATED` |
| `Apply` | бэкап (`backup_directory`), снимок `43`, `42` и `11` с `-Apply` по замороженным манифестам, повторный холостой `11`, снимок после | 0 строк осталось, ни одна таблица не выросла |
| `Verify` | `40` + `41` на результате, `45` против `source_database` | `gate=PASS`, `DELETE 0`, сверка `PASS` |

`Apply` берёт последний `DryRun` (или `-DryRunDirectory`) и проверяет, что
манифесты не изменились. Если база — одноразовая копия, бэкап можно
пропустить (`-SkipBackup`).

Если `DryRun` остановился на `gate=BLOCK`, разобрать:
- `closure\boundary-references.csv` — остающаяся строка ссылается на чужое;
- `closure\cascade-blocked.csv` — каскад упёрся в защищённый тип;
- `closure\clear-row-candidates.csv` — табличная строка ссылается на удаляемое;
- `delete_unmarked_organizations` — организации без пометки → `Prepare`.

Каждое решение — строка политики и запись в `DECISIONS.md` конфигурации. Если
решение верно везде — в `policies/`, если только для этого выделения — в слой
прогона (`policy_layers`).

## После Apply: 1С

Нужен пользователь 1С. Если 1С не пускает (например, не добавляется пользователь),
откройте ИБ в режиме обновления. Порядок: обновление ИБ → ТиИ с пересчётом
итогов → проверка итогов `49` → `47` (догнать итоги, доступ).

### Обновление ИБ

```powershell
& 'C:\Program Files\1cv8\8.3.27.2214\bin\1cv8c.exe' ENTERPRISE /S 'server\zup_copy' /N admin /P '' `
  /C ЗапуститьОбновлениеИнформационнойБазы /DisableStartupDialogs
```

БСП выполняет обязательные обработчики, даже если версия не менялась
(в журнале «с 3.0.206.19 на 3.0.206.19. Приложение будет обновлено»): так
обновляются вспомогательные данные после удаления. Обновление идёт в фоне;
если оно короткое, формы прогресса не видно — результат смотреть в журнале
регистрации («Обновление информационной базы на версию … выполнено успешно»).
Закрыть клиент.

### ТиИ (`46`)

```powershell
.\scripts\46-run-tii.ps1 -InfoBase 'server\zup_copy' -User admin -Profile CheckAndTotals -PrepareCluster `
  -Database zup_copy -SqlServer server -CatalogDirectory <dry-run>\catalog `
  -DeleteManifest <dry-run>\closure\delete-manifest-with-cascade.csv -OutputDirectory <папка>
```

Профили:
- `Check` — логическая и ссылочная целостность, только тестирование; журнал
  разбирает `44`;
- `Totals`, `CheckAndTotals`;
- `Repair` — исправление, токен `TII-REPAIR`;
- `Rebuild` — реиндексация и реструктуризация.

Находки `deleted-by-run` — ошибки конвейера, `pre-existing` — дефекты исходных
данных: их тоже стоит проверить в копии до удаления.

### Итоги (`49`)

ТиИ пересчитывает итоги быстро (БИТ — 11 с), но в БИТ стабильно пропускает
`Хозрасчетный`, `бит_ОборотыПоБюджетам`, `РеализованныеТоварыКомитентов`.
`49` находит регистры, в итогах которых остались удалённые организации:

```powershell
.\scripts\49-check-stale-totals.ps1 -Database zup_copy -CatalogDirectory <dry-run>\catalog -OutputDirectory <папка>
```

### Обслуживание (`47`)

Открыть `MCP_Toolkit.epf` в тонком клиенте (порт свободный — 6003 может быть
занят чужим клиентом; первым вызовом проверить `СтрокаСоединенияИнформационнойБазы()`):

```powershell
& 'C:\Program Files\1cv8\8.3.27.2214\bin\1cv8c.exe' ENTERPRISE /S 'server\zup_copy' /N admin /P '' `
  /Execute <путь>\MCP_Toolkit.epf /C 'startup;mode=embedded;port=6013'
.\scripts\47-post-delete-1c-maintenance.ps1 -ToolkitUrl http://127.0.0.1:6013 -RecalcTotals `
  -TotalsRegister <stale_registers из 49> -SequenceReport -StartAccessUpdate -OutputDirectory <папка>
```

- пересчёт итогов `ПересчитатьИтоги()` — регистров из `49` (без
  `-TotalsRegister` — всех); затем `49` ещё раз, должно быть 0;
- границы последовательностей (восстановление = перепроведение, делает
  пользователь);
- обновление доступа БСП: универсальный режим — фоновое задание, стандартный —
  перестроение регистров доступа и ролей.

### Файлы на томах (`Files`, `50`)

Файлы сохраняемой организации из томов загружаются в базу, тома отвязываются:
копия перестаёт ссылаться на боевое хранилище. Нужен открытый `MCP_Toolkit`
(`toolkit_url` в настройках).

```powershell
.\scripts\Build-1CTools.ps1                                   # build\1c\ПодготовкаКопииПослеВыделения.epf
.\scripts\Invoke-Extraction.ps1 -Settings $s -Stage Files     # сводка, доступ, проверка
.\scripts\Invoke-Extraction.ps1 -Settings $s -Stage Files -ConfirmationToken LOAD-FILES
```

- Сервер 1С читает файлы под своей учётной записью. Если он не видит тома
  (`Access` = `NO_ACCESS`), откройте обработку в 1С и на вкладке «Файлы на
  томах» сохраните учётку хранилища для сервера («Сохранить для сервера 1С»:
  `cmdkey` из серверного кода, пароль учётки сервера не нужен). Или скопируйте
  файлы и задайте `volume_path_substitution` (`"\\server\share\ => D:\copy\"`).
- Проверка не читает содержимое: только наличие и размер.
- Загрузка не удаляет и не меняет файлы на томах; можно прерывать и повторять.
- Файлы, которых нет в хранилище, — в `load\file-errors.csv` с владельцем и
  именем: их прикрепляют пользователи. Их тома остаются; отвязать и их —
  `50-volume-files.ps1 -Action Unbind -IncludeVolumesWithFiles -ConfirmationToken UNBIND-VOLUMES`.

### Перезагрузка через `.dt` и сжатие (`Compact`, `51`, перед выдачей)

Удаление в SQL оставляет в служебной таблице `BinaryData` двоичные данные
удалённых объектов (в БИТ — 85 ГБ из 105 ГБ). Выгрузка и загрузка `.dt`
оставляют только используемые, затем `48` сжимает файлы:

```powershell
.\scripts\Invoke-Extraction.ps1 -Settings $s -Stage Compact -ConfirmationToken RELOAD-DT
```

- бэкап перед загрузкой (`-SkipBackup`, если он уже есть), `.dt` и бэкап
  остаются в `backup_directory` — удалить, когда база принята;
- `51` сравнивает число строк каждой таблицы до и после: меняться может
  только `BinaryData` и служебная `_ExtensionsRestructNGS`, иначе остановка;
- нужен монопольный доступ (сеансы завершаются, регламентные задания
  блокируются);
- перед сжатием база переводится в модель `SIMPLE`: в `FULL` без резервных копий
  журнала журнал не усекается и при сжатии файла данных растёт (ЗУП — до 13 ГБ);
- загрузка заменяет часть значений «Хранилище значения» заголовком `STORHDR` со
  ссылкой на `BinaryData`. Сверка `45` сравнивает такие значения по содержимому;
  их число — в колонке `external_values`.

Если загружать в новую базу (сравнить с исходной), создавать её с тем же
сдвигом дат: `rac infobase create … --date-offset=2000`. Без него даты в SQL
отличаются на 2000 лет и таблицы не сравнить напрямую. У новой базы
отличаются только колонки «Хранилище значения» — в них ключи `BinaryData`,
которые создаются заново.

## Скрипты по отдельности

`Invoke-Extraction` только вызывает скрипты по порядку, их можно запускать и
вручную. Организации задаются `-Organization` (ссылки, можно несколько) или
`-OrganizationCode`; в `11` — `-PreservedOrganization`. Параметры каждого
скрипта описаны в его заголовке; [`scripts/README.md`](../scripts/README.md) —
список.

## Известные ограничения

- Связи «через код» и по строковым ключам граф не видит: системный слой
  защищается `PROTECT`, всё найденное на проверке добавляется в политику.
- `boundary-references.csv` показывает один источник ссылки.
- `MCP_Toolkit` обрывает запрос через 180 с (ответ 504), хотя 1С может
  продолжать работу. Регистр, на котором `47` получил 504, пересчитать повторно.
- Файлы на томах (`ТомаХраненияФайлов`) удаление в SQL не трогает: их загружает
  в базу стадия `Files`.
